# SITE-11

Card: SITE-11 Learn more page: Compliance Management (NH-216, epic NH-202)

Test files: `site-11.spec.ts`, `support/site-11/page.ts` (the Compliance page's own checks), `support/site-11/build.ts` (the production build and a static server for it), `support/site-11/files.ts` (the AC-12 file rule).

Spec: [NH-216](https://obsydian.atlassian.net/browse/NH-216)

Locks: acceptance-lock/site-11

It imports, and never edits, `support/site-08/learn-page.ts` and `support/site-08/kit.ts` (SITE-08, NH-213: the page helper, with the child lock site-08.1 that waits for fonts, and the kit oracle) and `support/site-01/public-site.ts` (the Cognito and API patterns of SITE-01). It needs SITE-08 merged: without `support/site-08/` the spec does not load. Before every region compare against the kit (demo steps included), `compareRegion` makes both pages wait for `document.fonts.ready`, sends a `resize` event and sleeps 150ms (`fontsAndResize`, its own copy), so the kit's measuring scripts run again on the loaded font; the SITE-08 helper does the same for its own checks. It shares no file with SITE-09 or SITE-10 (the same method, its own copies).

## How the tests run

```
E2E_BASE_URL=http://localhost:4200 npx playwright test -c e2e/acceptance/playwright.config.ts site-11
```

Every test runs at 1280 and 390 wide, except AC-3 (1440 and 390: the kit's desktop screen is 1440) and AC-12 (reads the repository and the build once, in `desktop-1280`). The browser starts with `--disable-lcd-text --font-render-hinting=none`. The build (`npm run build`, which runs `verify:design` first and `verify-public-names` last) runs once per test run, in AC-1, and AC-2 and AC-12 read the same output. `SITE_11_BUILD_DIR` points the tests at an existing build output instead (for trying a changed output by hand; CI does not set it).

### The kit ref

The spec sets `SITE_KIT_REF` to it for its own tests only (and puts the old value back afterwards, so no other spec in the run is changed). The helper's default, the ref in `sync.json` (e9a352f), has the closing band note and the older reduced motion scripts. A later kit change needs a new pin.

## Contract (what the builder makes)

1. Route `/product/compliance`, lazy, in `site.routes.ts` (`canActivate: [siteStyles]`, title "Compliance Management · Naleko People"), and `{ path: 'product/compliance', renderMode: RenderMode.Prerender }` in `app.routes.server.ts`. The page lives in `src/app/ds/site/learn/compliance/` (at least one `.ts` file that is not a spec).
2. The page is one `h1`, one `main`, the header and the footer. A `.pp-site-form-page--learn` hero (the Learn more page top) is a child of the one element that also holds the sub-menu, the demos, the ending and the closing band (the SITE-08 helper takes its root from it: `.pp-site-form-page--learn`'s parent). The footer may sit in that element or outside it (it is judged by its own check).
3. Section ids exactly: `requirements`, `register`, `reminders`, `renewals`, `not-cleared`, `questions` and the closing band `demo`, each once, each element named by a heading inside it through `aria-labelledby`. Sub-menu tabs in that order, named "Requirements per role", "Certificate register", "Reminders", "Renewals read", "Not cleared to work", "Questions", with `#` targets.
4. The hero card is `.pp-site-hcard[data-demo="hcard-compliance"]`. The demos are `section.pp-site-demo` with the kit's classes (`pp-site-req__*`, `pp-site-register__*`, `pp-site-timeline__*`, `pp-site-read__*`, `pp-site-clear*`, `pp-site-suggest`, `pp-site-state__item--on`, `pp-site-step--in`, `pp-site-demo__again`), `data-site-live` once started. **Four of the five have a `button.pp-site-demo__again`; the certificate register (`#register`) has none in the kit**: its filters cycle on their own (all, expiring in 30 days, overdue, all, ...) from 2.6s after it is in view, one change every 3.2s, until a click on a filter, which answers at once and stops the cycle for good. The spec's AC-7 says "Play again replays it"; the kit has no such button, so the tests follow the kit (the same rule as SITE-08 and as the sample phone of SITE-10: the tests follow the kit and the difference is logged). A builder who adds the button changes the words and the page parity (AC-2, AC-3) fails.
5. A demo starts when 15% to 60% of it is in view (the kit starts at 35%; the spec says 15%; the tests judge "not at 12%, started at 60%"). Once started it plays once, keeps its place and replays from its first step with Play again, which keeps focus. The register is judged the same way, by its first filter change (3.6s at 12% in view: none; 4.5s at 60%: one).
6. `data-site-still` on the `html` element: every demo and the hero card show their last step at once and nothing loops: the hero card's restart and the register's cycle included (the kit's own scripts ignore the attribute; the register has no last step, so under it the register shows one state, any, and changes no filter). Under `prefers-reduced-motion: reduce` every demo, the hero card and Ask Batsi keep the kit's timings (fades, colour changes, counts, ticks, slow light and drift, loops at the kit's slower durations); no script slides anything (`element.animate` of a transform); grain, a flying card and pointer tilt do not exist on this page in the kit.
7. Links with `href="#"` do not matter to these tests (the spec leaves link targets to SITE-16).

## Where the card and the tests differ

- AC-7 "Play again replays it": the kit's certificate register has no Play again; it cycles its filters on its own and answers a click (see the contract); the tests follow the kit. To be confirmed with the BA: either the spec line goes, or a design system change adds the button (then the kit is re-pinned). The register has no first and last step either: "first step and last step each match the kit's markup" is judged as the three filter looks (all, expiring, overdue), each as a picture.
- AC-5 runs SITE-08's `checkSubmenu` with `deaf: true` (demos stay on their first step) on a page opened under `prefers-reduced-motion: reduce`, so the kit's own rule makes the sub-menu's scroll instant. The helper's tap check scrolls past all five demos; with smooth scrolling on a busy machine the scroll starts late, the kit's 180ms settle re-aims it mid-animation and the page ends far from where it should (SITE-09 lock check, AC-5). The landing position (112px, 4px) is judged as before, and in normal motion by `tapInNormalMotion`; smooth scrolling of the shared sub-menu is SITE-08 AC-4's.
- AC-11 runs `checkMotion` on a page whose open step switches off the transition of the phone header's menu button (`.pp-site-header__burger`, the shared header). SITE-08's colour allowance names `pp-button` as the first class and the burger's first class is its own, so the helper counts the burger's `background-color` transition as a problem. Open question for the SITE-08 owner: widen the allowance (the same note as SITE-09 and SITE-10).
- Each picture of a region counts only when the region sat still before and after it (a demo elsewhere can change height while the pictures are taken).
- Pixel checks photograph both pages scrolled to the top, so the sticky header and sub-menu sit over the hero and not over the region compared.
- Start threshold: the card says 15%, the kit starts at 35%. The tests judge "not started at 12%, started at 60%", so any threshold from 15% to 60% passes (as SITE-08).
- AC-3 desktop is read in a 1440 window (the kit's desktop screen); the other desktop checks use the project's 1280 window, where the kit page's stage takes the window's width too.
- The footer sits outside the helper's page box on a build that uses `PpSitePage` (the footer is projected after `main`), and inside the kit's. So the helper's whole-page checks leave it out on both sides (`omit`), and the footer has its own words, box and pixel checks.
- The hero card's last step under `data-site-still` is read from the kit's own run (its state between the last step at 7.6s and the restart at 11.8s), since the kit's script shows the first step, not the last, under `data-site-still`.
- Under `data-site-still` the kit's demo scripts do nothing (they ignore the attribute); the end state is the end of the kit's own run on a live page, and the app is judged against it. The register has no end state; the tests ask only that it does not cycle (one state, no filter change). A builder may show any of its three looks.
- The kit's static markup (before any demo starts) shows each demo's last step and the hero card's first; AC-3 compares the page in that state, as the kit draws it (the spec's "first step" there means the kit's resting state).
- AC-11 "tilt", grain and a flying card: the kit's Compliance page has none, so there is nothing to judge; reduced motion is judged on what the kit has (timings, no script slides).
- Link targets ("Book a demo", "Get started", "Learn more") are not judged (SITE-16).
