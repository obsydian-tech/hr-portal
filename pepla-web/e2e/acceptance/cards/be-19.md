Test files: `be-19.spec.ts` and `support/be-19/`, copied from `support/be-18/` with code added only. The
added code:
- `fake-aws/cjs-hook.cjs` (new), loaded with `node --require`. The old admin, IT and provisioning Lambdas
  are CommonJS, and `require()` does not go through the ESM hooks, so this sends their AWS SDK names to the
  same fakes.
- `OLD_HANDLER` names those 17 handlers, each with the answer it already gives a caller it refuses.
- `ID_TOKEN_FILE` is the new `lambda/shared/id-token.js`.
- A caller can be raw claims (`claims`) or a Lambda authorizer that names a staff id (`lambdaStaff`).
- `fn-rule.mjs` also reads a CommonJS file's exports from its default export.

Lock: acceptance-lock/be-19

Nothing here opens the app. All five tests run once, in `desktop-1280`.

- **AC-1** runs talentFlowApproveAction's approve and reject. The approver comes from an HR ID token's
  `custom:staff_id`. Everyone else gets the refusal, with nothing written and no event. That includes an
  empty `custom:staff_id` and near-miss groups (`naleko-talentflow-admin`, `hr_staff_readonly`, `HR_STAFF`,
  `TalentFlowAdmin`). The approve and reject logs name the token's staff id.
- **AC-2** runs the file link for twelve stored file names (TAB and DEL among them) and reads the Content-Disposition the URL is signed with.
- **AC-3** runs the upload link with a marked file name. No log line holds the name or the S3 key.
- **AC-4** runs the 17 old handlers with non-ID tokens (exact existing refusal, no AWS call) and with ID
  tokens (past the check, and never a 401 or 403 before an AWS call). It compares `id-token.js` with `hr-group.mjs`, and checks that each handler
  requires `../shared/id-token`.
- **AC-5** runs the own list for a missing id, as an employee, as HR, and with an HR access token (403).

Words: the approve and reject refusal is "You do not have permission to perform this action.", the
sentence the old app already shows for a 403 from these routes. Every other answer is the route's existing
text.
